# 开发者提交规范、行为准则和拒收规则

## 目的

CardputerZero AppStore 希望成为一个安全、透明、可持续的 CardputerZero 应用 registry。提交到 AppStore 的应用需要尊重用户、设备、维护者、开源社区和适用法律。

本规则适用于：

- 应用元信息。
- 源码。
- 二进制文件。
- 图标和截图。
- 应用描述。
- Pull Request。
- Issue 和评论。
- 任何提交到 registry 的相关材料。

## 开发者基本要求

开发者必须：

- 提交准确的应用元信息。
- 清楚说明应用用途。
- 声明所有数据访问、设备访问、网络访问和外部硬件需求。
- 提供可用图标，尽量提供截图。
- 提供有效下载地址和 checksum。
- 声明应用是开源、源码可见、闭源、binary-only，还是混合模式。
- 声明 license 和是否允许商用。
- 不做误导性宣传。
- 善意回应维护者 review。
- 在发现关键安全、隐私或设备风险时及时修复。
- 下载地址变化时及时更新元信息。

## 元信息真实性

应用元信息是用户信任模型的一部分。开发者不能隐藏或误导以下信息：

- 是否收集个人数据。
- 是否读取设备唯一标识。
- 是否联网。
- 是否访问摄像头、麦克风、GPS、传感器、文件系统或外部硬件。
- 是否后台运行。
- 是否存在付费功能、商业限制或 license 限制。
- 已知的设备风险、高 CPU 使用、高存储使用或电量影响。
- 是否需要 Meshtastic LoRa Module 等外部模块。

如果应用后续版本改变了这些行为，必须在发布新版本前或同时更新元信息。

## 隐私要求

访问、保存、上传或处理用户数据的应用必须声明：

- 访问哪些数据。
- 为什么需要这些数据。
- 数据是否离开设备。
- 数据会发送给谁。
- 数据保存多久。
- 用户是否可以删除数据。
- 是否与第三方共享数据。

应用应遵守最小必要原则。超过功能合理需要的数据收集，可能导致拒收或下架。

## 设备安全要求

应用不得故意损坏设备，也不得制造不合理风险。

涉及系统设置、存储、网络、GPIO、传感器、电源、音频、显示、外部模块或类似固件级行为的应用，必须明确说明可能风险。

以下情况可能被拒收：

- 未说明的设备不稳定风险。
- 未经用户明确同意就可能破坏用户数据或系统文件。
- 永久改变设备行为但没有恢复路径。
- 可能导致硬件过热、过载或超出合理使用范围。
- 向用户或审核者隐藏高风险行为。

## 用户体验要求

应用应达到基本可用标准：

- 能从 APPLaunch 或真机 AppStore 启动。
- 有可识别的应用图标。
- GUI 应用应适配 CardputerZero 的 320 x 170 屏幕。
- 不能把用户困在应用里，必须有清晰退出方式。
- 正常使用时不能一启动就崩溃。
- 不能故意展示欺骗性 UI。
- 如果是实验性、未完成或需要特殊设置，必须明确标记。

体验过差的应用可以被要求修改，严重时可以拒收。

## 不接受的应用类型

以下应用或内容可能被拒收、隐藏或下架：

- 违法用途。
- 恶意软件、间谍软件、凭据窃取、未授权持久化、未授权访问。
- 未声明或超出合理范围的用户数据收集。
- 基于种族、民族、国籍、性别、性别认同、性取向、宗教、残障、年龄、种姓等身份的歧视或骚扰。
- 仇恨言论、去人性化内容、定向骚扰。
- 战争、武器化、监控、目标识别或伤害用途。
- 主要用于伤害他人、规避执法或促进暴力的功能。
- 未授权追踪、跟踪或骚扰。
- 侵犯版权、商标或 license 的内容。
- 欺诈、诈骗、钓鱼或冒充他人。
- 隐藏的付费、商业化或授权限制。
- 未声明但可能造成设备损坏或用户数据损坏的行为。
- 故意绕过 registry 审核或安装策略的应用。
- 多人可信投诉后，经维护者和项目管理层投票决定取缔的应用。

这不是穷尽列表。维护者可以拒绝明显带来安全、法律、隐私或社区风险的提交。

## 高敏感应用审核

以下类型需要更严格审核：

- 闭源或 binary-only。
- 摄像头、麦克风、GPS、网络、用户数据或文件系统访问。
- 后台服务。
- 控制外部硬件模块。
- 包含支付、账号登录或云服务。
- 修改系统设置或安装额外服务。
- 面向儿童、教育、医疗、安全等敏感场景。

维护者可以要求开发者提供源码访问、额外声明、截图、测试日志、可复现构建或人工演示。

## 审核和执行

维护者可以：

- 要求修改元信息。
- 要求修改代码或打包方式。
- 把应用标记为实验性或高风险。
- 拒收应用。
- 标记应用为 deprecated。
- block 或下架应用。
- 在应用行为变化后要求重新审核。

可能下架的情况：

- 违反本规则。
- 产生明显用户、设备、法律或隐私风险。
- 应用长期无人维护且已经不可用。
- 下载地址失效或变为不安全地址。
- 收到多名用户可信投诉，并经维护者或项目管理层投票决定下架。

## 申诉流程

开发者可以通过 Issue 或 Pull Request 申诉拒收或下架决定。申诉应包含：

- 应用 UUID 和标题。
- 简短说明希望改变什么决定。
- 说明问题已经修复，或说明原判断存在误解。
- 如有需要，提供更新后的元信息、源码或 release 链接。

维护者应尽量记录最终决定。

## 维护者原则

维护者应：

- 尽量一致地执行规则。
- 优先给出明确解释，而不是静默拒绝。
- 不接受隐瞒隐私或设备风险的应用。
- 把用户信任放在应用数量之前。
- 让规则对业余开发者也保持可操作。
- 规则变化应在仓库中公开记录。

## 最低准入检查清单

应用通过审核前至少应满足：

- 必填元信息完整。
- UUID 合法且唯一。
- 分享码唯一。
- 标题、简介、图标、作者存在。
- 下载地址有效。
- license 和商业使用条款已声明。
- 源码开放程度已声明。
- 权限和数据访问已声明。
- 外部硬件需求已声明。
- 已知设备风险已声明。
- 不违反拒收规则。
